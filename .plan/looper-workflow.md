# Looper: conversation to ticket to Git brief

Updated: 2026-11-19. Status: implemented POC workflow; a synthetic live DeepSeek welcome/full-name conversation has been verified.

## Entry and continuity

**Looper** is the floating chat button on the main page. It opens the last conversation used in this page session, or resumes an existing draft after reopening the app. If neither exists, it starts a draft. Closing and reopening Looper does not create another ticket. **New conversation** inside the dialog starts a separate request and keeps the old one in My requests.

Saved requests can also be reopened from My requests, or All tickets for Master users. Confirmed requests are stored in `.data/requests.csv` by the existing Vite server. Master sees all saved tickets; Administrator and other roles see only their own user/account tickets. Other requesters' tickets are read-only for Master. Drafts stay in the browser, and CSV download remains optional. There is no folder setup.

## The three stages

| Stage | Purpose | Handoff |
| --- | --- | --- |
| Conversation | Looper asks focused questions and updates a structured draft, using the curated capability context. Confirmed facts, assumptions, missing data, and unsupported API/tool work stay distinct. | User chooses Review ticket. Chat alone does not submit or approve anything. |
| Ticket | User edits/reviews the draft. Title, problem/use case, desired behavior, and acceptance criteria are required. Other unknowns can remain explicit scoping questions. | Confirm and save request writes the local server CSV, sets Submitted, and opens Git brief review only if saving succeeds. |
| Git brief | Show the GitHub issue body generated from the confirmed ticket revision. User reviews scope, unknowns, and private content. | Mark ready for Git enables copy/Markdown download. Actual issue submission and build approval are separate later actions. |

The ticket is the working record; the Git brief is a reproducible handoff from it. The brief is not generated by another model call, so an export cannot silently invent requirements beyond the ticket.

## Audience and destination

The POC currently exposes all three stages to logged-in users for testing. Recommended audience separation, discussed with the owner: regular requesters confirm the ticket and see request status; product owners/engineers review the Git brief internally. That split and its role mapping are not implemented yet.

The brief is generated on demand from the confirmed ticket restored from the local CSV. Its Markdown text is not independently stored or synchronized to GitHub. Copy puts it on the clipboard; Download Markdown saves `REQ-<id>.md` via browser download settings. No file is automatically added to the source repository.

The later intended destination is a GitHub issue body in the selected product repository after internal triage accepts the request. Issue URL linkage, submission credentials, repository selection, and code automation remain outside this capture MVP.

## What the Git brief contains

- A short feature title.
- Stable request ID, revision, capability catalog version, and scope assessment.
- Problem/use case, current behavior, and desired behavior.
- Included frontend work and explicit exclusions.
- Observable acceptance criteria.
- Data needed and dependencies/capability evidence.
- Assumptions and open questions, including unverified API/library support.

Unfilled optional fields are marked as questions for scoping. The brief does not assert that an unknown API exists or that a candidate library/provider is approved. Account metadata and private conversation are not appended. Known identity/token values are redacted, but the human must still review any private information typed into the ticket.

The export is Markdown suitable for a GitHub issue description. It is not a commit, code diff, branch, PR, implementation plan approved by the product owner, or a promise to build the feature. Repository selection, issue creation, and the later approved-scope coding trigger are outside this capture MVP.

## Example: a map request

A customer asks to see assets on a map. The conversation establishes which assets, the desired interactions, and what success would look like. The ticket can specify markers, a details popup, and filtering while recording that coordinates, a map renderer, and a tile provider still need verification.

The Git brief carries those exact requirements and questions. Its scope assessment can remain Needs scope review. A reviewer can accept the brief for issue scoping without pretending the implementation is already feasible. A request explicitly requiring excluded API/tool development cannot be marked ready until narrowed/reviewed.

## State and revision rules

| Record state | Meaning |
| --- | --- |
| Draft / needs_review | Conversation or edits are still being confirmed. |
| Submitted / needs_review | Ticket saved successfully; Git brief awaits human review. |
| Submitted / ready_for_git | Human reviewed the brief and it is available for copy/download. No issue or build has been started. |

Editing a submitted ticket or sending more requirements returns it to Draft, increments its revision once, and clears readiness. It must be confirmed and reviewed again. Revisions retain the same request ID. A new independent idea should use New conversation.

Provider failures keep the conversation/draft for retry. Failed CSV saves keep the user in Ticket and do not advance to Git brief. A browser-cache failure does not invalidate a successful server save. Scope assessment of Outside current scope blocks Git readiness even after checking the review box.

The handler tolerates partial ticket objects and text-list fields without dropping prior draft values. It makes at most one format-repair retry for invalid, blank, or truncated model output; transport/provider errors are reported separately. The capability catalog documents the existing AuthUser.name/username fields and their login-response mapping, so a full-name greeting can use the current profile and existing fallback rather than requiring a new endpoint.

## Next automation boundary

The owner added an operator-run script, `scripts/Publish-GitBrief.ps1`, for downloaded Markdown briefs. It uses Codex's read-only execution mode to review the brief against code/docs, checks all open/closed issues through paginated GitHub CLI requests, and publishes an actionable issue to `tellalli/autoloop` by default. Exact Request ID matches return the existing URL; Codex also checks semantic duplicates. Reviewed output includes problem/outcome, scope, acceptance criteria, implementation context, verification, and nonblocking questions. Blocking questions or failed checks stop publication. A dry run prepares output without creating an issue.

Keep downloaded briefs in `.data/gitbrief/`; artifacts and URL receipts are under its ignored `runs/` subdirectory. Source briefs stay unchanged. This is separate from the app: Mark ready for Git still only prepares the export, and the script does not update ticket CSV/status or add GitHub credentials to the app. The local script uses existing Codex/GitHub CLI sign-ins. Coding still needs the separate approved-scope gate; the script performs no implementation, commit, PR, or release.
